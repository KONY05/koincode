## Decision

Worth building — real use case (quick throwaway question without leaving the terminal), reinforces the local-first/privacy positioning, small surface area if scoped right.

**Granularity for v1: whole-session, decided before the first message is sent — not mid-session toggling.** The note describes both ("session starts with incognito on" and "toggle on/off during a session"). These aren't equal cost. The current wire protocol is session-ID-and-DB-dependent, not history-dependent: each turn the CLI sends only the newest message + `sessionId` (`use-chat.ts:299-316`), and the server rebuilds everything else by re-reading `Message` rows from the DB (`chat.ts:105-128`). A whole-session-incognito mode can bypass the DB entirely for that session. A true mid-session toggle would require the server to switch from "DB is authoritative" to "client is authoritative" partway through a conversation — solvable, but a materially bigger lift for a rarer case. Ship the whole-session version first; revisit mid-session toggling only if it's actually missed.

## Scope (v1)

- `/incognito` toggles a pending flag on the **NewSession** screen, before the first message is sent. Once the first message goes out, the session is locked into whatever mode it started in.
- While incognito: no `Session` row, no `Message` rows, ever. Nothing to clean up on exit — there's simply nothing written.
- Existing BUILD-mode tool execution (file writes, edits, bash) is **unaffected** — incognito only concerns chat-history persistence, not the filesystem side effects of tools the model runs. Worth stating explicitly in the UI copy so a user doesn't assume incognito makes edits/bash calls invisible too.
- Reopening the app after closing an incognito session loses that history — matches the note's "this is fine, it's for privacy not convenience."

**Deferred, not in v1:**
- Mid-session toggling on/off.
- Per-message granularity (mixed incognito/saved turns in one session).
- A persisted default/preference (e.g. "always start new sessions in incognito").

## Design

### 1. Entry point (`packages/cli/src/screens/new-session.tsx`)

Add an `isIncognito` boolean toggled by `/incognito` before the session-creation call. When set, **skip** the eager `apiClient.sessions.$post` call (`new-session.tsx:43-70`) entirely — sessions are created eagerly today (before the first message is even sent), so incognito must short-circuit that, not just message writes. Generate a client-side-only id (`crypto.randomUUID()`) to key React state/navigation instead of a real `Session.id`. Home screen's session list is unaffected by construction — nothing was ever written for it to list.

### 2. Wire protocol: full-history mode for incognito turns

Normal turns send `{ id: sessionId, messages: [justTheNewMessage(s)], ... }` (`use-chat.ts:299-316`) because the server reconstructs prior turns from the DB. Incognito sessions have no DB rows to reconstruct from, so `prepareSendMessagesRequest` needs an incognito branch: send the **full** `chat.messages` array every turn, plus an `incognito: true` flag, and omit `sessionId` (or send the client-only id purely for logging/UI correlation, never for a DB lookup).

**Storage location: client, not server — decided.** The full history already lives in the CLI's `useChat` React state for every session, incognito or not (that's the status quo, not new work); the question was only whether the *server* should also keep an in-memory copy so the client could go back to sending just the newest message. Rejected: it would make the server stateful (a `Map<sessionId, Message[]>` with no signal from the CLI for when a session is "done," so entries would need a TTL or leak until restart), and it would be actively wrong given `server-manager.ts`'s existing 30-min idle auto-shutdown/respawn — an in-progress incognito conversation would silently lose its history on that respawn. Sending full history per turn keeps the server genuinely stateless per request (matching `code-standards.md`'s "server = AI orchestration only"), and the resend cost is irrelevant over CLI↔server loopback.

### 3. Server (`packages/server/src/routes/chat.ts`)

New branch, gated on `incognito: true` in the request body:
- Skip the session lookup/404 (`chat.ts:109-112`) and the DB-based context rebuild (`chat.ts:105-128`) — use the client-supplied full `messages` array as the complete context instead.
- Skip the pre-save `createMany` (`chat.ts:212-238`) and the `onFinish` post-save (`chat.ts:320-411`), including the `session.updatedAt` bump. Stream the model response exactly as today; just never touch `db.session`/`db.message`.
- No schema change needed for v1 — since incognito never touches the DB at all, there's no need for an `incognito` column on `Session`/`Message`. That's the main simplification this scoping choice buys.

### 4. Visual indicators

- **Mode label**: `StatusBar` (`packages/cli/src/components/status-bar.tsx`), rendered inside `InputBar` (`input-bar.tsx`), already shows the PLAN/BUILD label as the leftmost segment of its row — swap that segment's text to **"Incognito"** (own distinct color) when active, rather than inventing a new top-right corner element or an icon. Decided against an emoji/icon glyph: OpenTUI renders text cells, not vector graphics, so a literal icon isn't renderable at all, and unicode emoji width is inconsistent across terminal emulators (real jitter risk in a fixed-grid status row). Plain text also matches how PLAN/BUILD already render — no icon there either.
- **Input bar border**: `InputBar`'s outer `<box border={["left"]} ...>` already picks its border color conditionally by mode (`input-bar.tsx:~1121-1136`, a ternary on `colors.primary`/`colors.planMode`). Extend that same ternary to also swap `customBorderChars` to a dashed vertical character when incognito, matching the note's "dashes to indicate."
- **Message bubbles**: `components/messages/user-message.tsx`/`bot-message.tsx` — apply the same dashed-border treatment for messages sent during an incognito session, so the whole transcript reads visually distinct, not just the input bar.

## Package boundaries

Touches `cli` (new-session screen, use-chat, input-bar, status-bar, message components) and `server` (`routes/chat.ts`). Per `ai-workflow-rules.md`, that's a CLI-UI-change-plus-server-orchestration-change combination — split into two implementation steps: (1) server-side incognito branch in `chat.ts` first, verifiable alone via a direct API call with `incognito: true` and no `sessionId`; (2) CLI wiring (toggle, wire protocol branch, visual indicators) second, once the server contract exists.

## Resolved questions

- **`/incognito` typed after a session already has messages**: toast explaining it only applies to new sessions in v1 (no-op otherwise). Revisit when/if mid-session toggling ships — the toast goes away at that point, not before.
- **Mode label**: plain text "Incognito" swapped in for the PLAN/BUILD label, no icon/glyph (see Design §4 above for why).
- **Interrupts vs. crashes, disambiguated**: a normal mid-turn interrupt (user hits stop/escape while the model is streaming) is not a crash — the CLI process is still alive, so the incognito session's in-memory history is untouched and the UI stays exactly as-is; this is the existing interrupted-state UX (Feature 07), unaffected by incognito. A genuine crash (CLI process dies) is different in kind: since nothing was ever persisted, the session is simply gone on next launch — no recovery path, no special messaging needed, because there's no state to recover. This is the feature working as intended, not a gap to fill.

## Open questions / deferred

- None remaining for v1 scope. Mid-session toggling, per-message granularity, and a persisted "always start incognito" default remain explicitly deferred (see Scope section above).

The handler branches on `incognito`: skips the `db.session.findUnique`/404, skips the entire DB-rebuild-and-merge block (now an inline `incognito ? validateUIMessages(messages) : (...)` expression rather than a duplicated function) since the client already sends full history, and the `onFinish` callback returns immediately without touching `db.message`/`db.session`. No schema/migration change, as scoped.
- **CLI wire protocol** (`hooks/use-chat.ts`): `useChat` gained a 6th param `isIncognito` (fixed for the hook instance's lifetime, captured straight into the transport's closure — never a reactive dep, since v1 has no mid-session toggle). `prepareSendMessagesRequest` branches: incognito sends the full `chat.messages` array plus `incognito: true` and `roots`, and deliberately does **not** reattach current mode/model onto historical messages (unlike the normal path) since each message already carries its own real per-turn metadata from when it was sent/streamed — reattaching would have corrupted the transcript's historical mode/model display.

Handled by branching both `initiateDelete`'s no-mutations-found fast path and `handleRevertConfirmResponse`'s post-revert step on `isIncognito`.

## Follow-up: mode/incognito interaction

Raised directly: since incognito only guarantees chat history isn't saved (not that filesystem side effects are), should incognito be locked to PLAN mode so there's a genuine "no trace anywhere" guarantee? **Decision: default, don't lock.**

- **Locking rejected**: forcing PLAN whenever incognito is on removes `writeFile`/`editFile`/`bash` entirely — if the user then wants the agent to save one thing during that session, there's no tool available to do it short of abandoning incognito (defeats the point) or introducing a third, hybrid tool contract (real architecture growth — this codebase's mode system is deliberately binary, `getToolContracts` returns exactly one of two sets, and a third tier means touching the mode enum, `switchMode` tool, the mode-switch confirm dialog, and system prompt construction everywhere they assume two states) for a narrow need.
- **Shipped instead**: `/incognito`'s command action (`command-menu/commands.tsx`) calls `ctx.setMode(Mode.PLAN)` the moment incognito turns on — a default, not a lock. Mirrors the existing "sensible default, always overridable" pattern already used for model/reasoning-effort resolution elsewhere in this codebase. The user can still press Tab (or `/agents`) to switch to Build themselves afterward if they explicitly want the agent to write real files during that incognito session — nothing is blocked, just nudged toward the common case (a quick, private, read-only question).
- **Related gap found and fixed while discussing this**: `StatusBar`'s mode segment previously showed **only** "Incognito" whenever incognito was on, completely hiding whether the underlying mode was Plan or Build — meaning there was no way to tell, from the status bar, whether the agent could currently write real files. Fixed: the segment now reads `"Incognito · Plan"` / `"Incognito · Build"` (prefix, not replace) — `status-bar.tsx`'s `modeLabel` derivation changed from `incognito ? "Incognito" : <mode label>` to `incognito ? \`Incognito · ${modeShortLabel}\` : modeShortLabel`, with no changes needed to the existing width-budget math or coloring logic since both already just read `modeLabel`/`modeLabel.length` generically.
- **Follow-up correction, caught by tracing the actual width math rather than assuming it was fine**: `modeLabel` is a *fixed, non-sheddable, non-truncated* cost in `StatusBar`'s layout budget — unlike `modelDisplayName`/`updateLabel` (which get `truncateText`'d with an ellipsis) or the voice/mcp/effort labels (which shed entirely under pressure), it always renders at full length and is subtracted from `availableForLeft` before anything else gets its budget. Doubling its width (`"Incognito · Build"`, 18 chars, vs the old `"Incognito"` alone at 9) meant the model name now truncated/disappeared far sooner than before — and at ordinary widths (~70 columns), the fixed cost alone could already exceed the computed budget, with no ellipsis fallback (the row is `overflow="hidden"`, so it would just silently clip on the right).
  - First fix pass abbreviated `"Incognito"` → `"Inc"` **unconditionally** — wrong per explicit correction: the full word should be the default look, only compressing under genuine space pressure, not always. Fixed properly: `availableForLeft` (previously computed further down the function) moved above the label derivation so it's available early; `modeFullLabel`/`modeAbbrevLabel` are both computed, and `modeLabel = modeFullLabel.length <= availableForLeft ? modeFullLabel : modeAbbrevLabel` picks the full `"Incognito · Build"` whenever it actually fits, falling back to `"Inc · Build"` only when it wouldn't. Same reasoning as before for *which* half compresses first (the word "Incognito", not "Plan"/"Build" — the mode has no other on-screen signal, while incognito-ness is already reinforced by the dashed input-bar/message border).
