# Contributing to KOINCODE

Thanks for your interest in KOINCODE. We want contributing to be straightforward — here's what tends to get merged and how to get set up.

Changes that are usually a quick merge:

- Bug fixes
- Support for a new AI provider or model
- Improvements to tool execution (`packages/cli/src/tools/`)
- Fixes for platform-specific quirks (macOS/Linux/Windows install & compile paths)
- Documentation improvements

Larger product or UI changes (new screens, new modes, changes to the PLAN/BUILD split) are easier to land if you open an issue to talk through the approach first — see [Feature Requests](#feature-requests) below.

## Requirements

- [Bun](https://bun.sh) 1.x

## Developing KOINCODE

Clone the repo and install dependencies from the root:

```bash
git clone https://github.com/KONY05/koincode.git
cd koincode
bun install
```

Run the CLI in watch mode:

```bash
bun run dev:cli
```
Run the server in hot-reload mode (only needed if you're working on `packages/server` in isolation — `dev:cli` spawns its own `@koincode/server` automatically):

```bash
bun run dev:server
```

### Project structure

| Package | Purpose |
|---|---|
| `@koincode/cli` | Terminal UI client (React 19 + OpenTUI). Owns UI and local tool execution. |
| `@koincode/server` | Hono API server (port 37420). Owns AI orchestration only — never touches the filesystem. |
| `@koincode/database` | Prisma schema + generated client. |
| `@koincode/shared` | Shared Zod schemas, model registry, tool contracts used by both CLI and server. |

Each package has a hard boundary — see `context/code-standards.md` and `context/ai-workflow-rules.md` for the full rules, but the short version:

- Tool calls are executed **client-side in the CLI**, never on the server. The server streams tool calls back to the CLI; it doesn't touch disk or run shell commands itself.
- `@koincode/shared` has no runtime dependency on the CLI or server — it only holds contracts.
- If a change needs to touch more than two packages, it's worth a sentence in your PR explaining why.

### Database changes

If you're changing the Prisma schema, see the "Data" section of `context/code-standards.md` — migrations are hand-written into `packages/server/src/lib/migrations.ts` (not generated by `prisma migrate`) so they apply identically across compiled binaries, npm installs, and curl/iex installs. A schema change needs both the Prisma schema update and a corresponding entry in that file.

### Building a standalone binary

```bash
cd packages/cli && COMPILE=true bash bin/build.sh
```

Outputs `dist/koincode-darwin-arm64`, `dist/koincode-darwin-x64`, `dist/koincode-linux-x64` depending on platform.

## Before opening a PR

CI runs typecheck, lint, and a smoke-boot test against a compiled binary on every PR. Run the first two locally before pushing:

```bash
bun run typecheck
bun run lint
```

There's no test framework in this repo yet — TypeScript strict mode and the CI smoke-boot check are the correctness net. If you can exercise your change through the actual CLI (`bun run dev:cli`), do that before marking the PR ready.

**Version bump:** CI blocks merge if `packages/cli/package.json`'s version isn't higher than what's currently published on npm. Bump it as part of your PR:

```bash
bun run version:patch   # or version:minor / version:major
```

## Pull Request Expectations

- Keep PRs small and scoped to one feature or fix — this matches how the codebase is meant to evolve (see `context/ai-workflow-rules.md`'s scoping rules). Don't mix CLI UI changes with server orchestration changes, or a schema change with unrelated feature work, in the same PR.
- Explain what you tested and how a reviewer can reproduce it — screenshots or a terminal recording for UI/TUI changes, a reproduction sequence of commands for everything else, e.g. "run koincode --openrouter-key xxx, start a session, type /setup, observe crash."
- Before adding new functionality, check it doesn't already exist elsewhere (e.g. in `lib/` or `providers/`).

### PR titles

Follow conventional commits, matching the existing commit history:

- `feat:` new feature or functionality
- `fix:` bug fix
- `docs:` documentation changes
- `chore:` maintenance, dependency updates
- `refactor:` code change with no behavior change
- `test:` adding or updating tests

Optionally scope it to a package: `feat(cli): ...`, `fix(server): ...`.

### Style preferences

Enforced by ESLint/TypeScript strict mode, plus a few conventions specific to this repo (full list in `context/code-standards.md`):

- Use `type`, never `interface` — for object shapes, unions, and aliases alike.
- Avoid `any`; validate unknown external input (user input, config reads, AI SDK responses) at the boundary.
- Keep route handlers and screen components thin — push logic into `lib/`/hooks rather than inlining it.
- Fix root causes rather than layering a workaround on top.
- Name files after the responsibility they contain, not the technology.

## Feature Requests

For anything beyond a bug fix or small addition, open an issue first describing the problem and your proposed approach. This is especially true for anything that would touch the PLAN/BUILD mode split, add a new operational mode, or change what runs locally vs. what talks to an external service — those are core product decisions documented in `context/project-overview.md`.

## Reporting Bugs

Open an issue with:

- What you expected vs. what happened
- Steps to reproduce
- Your platform (macOS/Linux/Windows) and how you installed KOINCODE (curl/npm/binary/source)
- Relevant output from `~/.koincode/server.log` if the bug involves the server or AI streaming
